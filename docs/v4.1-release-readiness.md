# Website v4.1.0 release readiness

This record covers local preparation of `release/v4.1.0` on October 21, 2026.
The production base is `2e8171e9`, the released v4.0.0 commit. Preparation started
from integrated candidate `59932d16`; runtime and asset review commit `72f5746a`
is included in this candidate. No push, pull request, remote merge, tag,
GitHub Release, or deployment is authorized by this preparation.

## Scope and versioning

The release adds the website history timeline and maintained v1, v2, and v3
archives, a private history-film studio, refreshed project discovery and product
previews, and the Timeline career layout. It also improves reading, search,
keyboard navigation, enlarged-text layouts, asset delivery, metadata, and offline
cache behavior. `CHANGELOG.md` contains the generated release notes.

`pnpm run version-packages` consumes the pending Changesets and sets the root
website package to 4.1.0. Historical apps keep their original version labels and
remain excluded from release versioning. The existing lockfile and dependency
versions are retained. Both resume PDFs were regenerated because their source
fingerprint includes the root manifest and shared render dependencies. All five
pages match the preserved release PDFs in extracted text and rendered pixels.

The preserved `fix/reveal-threshold-cleanup` checkpoint is intentionally excluded.
Its shared-runtime proposal changed custom reveal timing and was rejected; the
current site retains explicit viewport-entry thresholds and their regressions.
See [Tall reveal groups](lumen-integration.md#tall-reveal-groups).

## October 22 reliability qualification

Claude Code implementation and independent read-only reviews produced three focused
commits: `7428a8d3` (search, offline recovery, content dates, and the IPv6 parser),

card work through `64e698e0`, including Career ledger, Role folio, and Compact folio.
The final recovery follow-up is `3611605e`.

The changes cover these behavior boundaries:

- Search has a ten-second deadline for headers and JSON bodies. Retry preserves the
  current query, focus, and URL, and late requests cannot overwrite newer state.
- Offline page links retain query-driven UI, followed redirects cannot poison the
  navigation cache, and historical utility pages link back to the current homepage.
- Required and optional content dates reject invalid Date values while preserving
  the existing accepted formats. The development dependency override moves
  `ip-address` to 10.7.4; the final dependency audit reports no vulnerabilities.
- Webmention loading follows up to ten pages of 1,000 entries under one twelve-second
  deadline. It validates every page, deduplicates IDs, and rejects incomplete or
  inconsistent feeds. The deployment guide documents offset-pagination limitations;
  the diagnostic script accurately labels its first-page count.
- Technology snapshot titles now exceed WCAG AA contrast in both themes. Measured
  contrast is 4.977:1 in dark mode and 7.309:1 in light mode at 390px and 1440px.
  The card-focus test covers all eight current cards. Scroll restoration accepts the
  exact half-pixel boundary of native pixel rounding while retaining focus,
  visibility, and accessibility assertions.
- Network-first requests use a cached response after eight seconds without headers.
  A missing cache leaves the request waiting for the network, streaming bodies keep
  working, and late network success refreshes the cache. The manual browser workflow
  uses explicit read-only permissions and does not persist checkout credentials.

## October 23 search and release follow-up

Runtime commit `a2ce58e3` adds accent-insensitive and canonically equivalent search
matching while preserving the typed query. The same normalized two-character minimum
now applies to typing, deep links, URL updates, and recent-search storage. Empty and
combining-mark-only inputs cannot match the whole index; Arabic vowel marks remain
significant. Browser regressions failed against the preceding implementation before
passing with the fix.

Static HTML query variants now share one cache key while the network still receives
the original URL. Mutable data and asset queries remain exact. Real Chromium and
WebKit checks cover runtime-cached About pages with `Vary` headers, offline queries,
streaming, redirects, eviction, and recovery deadlines. The IPv6 development check
uses `[::1]`; its regression preserves unrelated worker registrations and cache data.
The test keeps the unrelated document open because WebKit discarded synthetic cache
bodies across document disposal even with both cleanup operations disabled.

The offline shell remains the intended eight-second fallback for uncached pages.
Removing it would leave stalled requests waiting indefinitely, so the review proposal
to change that behavior was declined. Its wording now distinguishes browser network
status from site availability. Cache-key deduplication does not erase a stored
response's original URL; the cache documentation and privacy page state that boundary.
The privacy page also describes Giscus receiving the page URL, including an open search
query. An isolated browser run confirmed the current public client behavior while
intercepting widget requests before they reached the provider.

## Publication and recovery

After separate authorization, push this prepared release branch and open its
pull request into `main`. Require the current GitHub checks and resolve all
review findings before merging. Because this branch already contains the version
bump and matching changelog, the existing Release workflow creates `v4.1.0` and
the GitHub Release from the merged `main` commit; a second version bump is not
needed. Cloudflare Pages deploys that reviewed commit through the existing flow.

Verify the deployed revision, then smoke-check the routes in the
[deployment runbook](deployment.md#release-flow), plus `/history/`, `/v1/`, `/v2/`,
`/v3/`, retired-content redirects, search, theme persistence, and both resume
downloads. Confirm archives remain excluded from indexing and their navigation
stays within the selected era. Local checks do not establish production results.

No data migration is required. If production verification fails, promote the
previous healthy Cloudflare deployment or revert the release through a reviewed
pull request, then repeat the smoke checks. Preserve published tags and archive
source snapshots; never move a published tag to repair a release.
